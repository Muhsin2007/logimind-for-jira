| D20 | 2026-11-09 | Closed loop in Jira (week 3): a `scheduledTrigger` (interval day; Jira picks the time) plus an admin "Run check now" diff the open risks against a chunked KVS snapshot (new / resolved / still open; the first run is a baseline that reports and creates nothing; a 10-minute KVS lock absorbs duplicate invocations). Auto-create is an admin setting, **off by default**: at most 5 issues per run, only for newly critical risks without an issue, created **asApp** from the D8 template (the scheduled run has no user); a missing permission is shown as a clear "the app cannot create issues in …" message. When a linked risk disappears, one "resolved in data" ADF comment is added (at most 10 per run, never repeated); LogiMind never transitions issues. The briefing is deterministic (no LLM). Supplier follow-up is drafted by the Forge LLM from the shipment facts only (CSV text passed as quoted data), checked like D15 (every ID, date and number must be in the facts) and falls back to a fixed template; it is copy-only and never sent. It counts against the per-person and copilot caps. No new scopes | The roadmap's "act on risks" gap without new permissions or costs: asApp is the only identity a scheduled run has; off-by-default and caps keep a misconfigured run harmless; comments instead of transitions respect each team's workflow; copy-only avoids any outbound e-mail scope |
| D22 | 2026-11-10 | Bonus fallback (week 4): add a `rovo:mcp` module (`logimind-mcp`, Preview) whose `tools` are the **existing** five `action` keys (all `actionVerb: GET`). | D23 | 2026-11-10 | Week 5 design. The stock chart reuses the days-of-cover rules (D18): usage at the average daily rate, arrivals at the start of their expected day, overdue arrivals ignored; reservations are covered first, and after a stock-out the line stays at 0 (lost sales, not backorders). The stock-out mark is the exact fractional crossing, so it always matches days of cover (pinned by a test over every demo position). The timeline shows at most 12 rows (overdue first) and counts a shipment as late from its planned date even if a newer ETA is earlier. Onboarding (welcome screen, checklist) is stored per person in `localStorage`, not KVS. Charts are SVG with `aria-hidden`; a text summary carries the meaning. No new scopes, no chart library | One projection everywhere, so the chart, the table and the Copilot never disagree; no dependency or storage to secure; screen readers get the same facts in words |
| D24 | 2026-11-11 | Supplier reliability and arrival forecast (week 6, author's choice "Надёжность + ETA"). Pure domain code (`supplier-reliability.ts`), recomputed on read like risks (D5). A delivery is a non-cancelled shipment with an actual arrival on or before today; delay = days after the planned date (early counts as 0). Grade needs ≥ 3 deliveries: reliable ≥ 90 % on time, watch ≥ 70 %, else unreliable. Usual delay = median, rounded up. Suppliers match ignoring case and repeated spaces. Forecast for an open shipment = plan + usual delay, only when later than the ETA; null when that date has passed. The stock chart's "late as usual" line moves only shipments not yet overdue (cover ignores overdue arrivals, D18), so it is never better than today's line. Not a risk rule; `RULE_VERSION` unchanged. Review LOW items accepted: the supplier record also appears in the Jira issue panel (same data any app user sees); the index is rebuilt per `getShipment` (≤ 2,000 rows, negligible); control/bidi characters in names are not stripped; the new fields are not passed to the Rovo/MCP actions (field allowlist) | Uses data customers already import (actual arrival dates), adds no scopes or storage, and turns a blind ETA into an honest, explainable "likely" date; median and a minimum history keep one bad delivery from labelling a supplier |

| D21 | 2026-11-09 | LogiMind roles: one **owner**, up to 20 **managers**, everyone else a **viewer**. A Jira site administrator claims ownership in Import & Settings (atomic, under a KVS lock); any Jira admin can take it over later (fallback when the owner has left). The owner adds/removes managers (found by name via `user/search` **asUser**) and hands over ownership (the old owner stays a manager). Owner and managers may do everything that needed ADMINISTER before (import, demo data, delete, Jira settings, auto-create, Run check now). Until an owner exists, Jira admins keep these rights (D7). Every mutating resolver checks the role server-side; role changes are pure functions applied to state re-read inside the lock. Only account IDs are stored; names and avatars are read from Jira asUser when Settings is shown and never stored. Role log: last 50 changes in KVS. New scope `read:jira-user` (major version) | Teams need logistics leads who are not Jira admins to run LogiMind, without giving them site admin. asUser lookups keep Jira's profile-visibility rules; storing IDs only keeps personal data minimal; the admin takeover prevents lock-out |
